## What each rule means

### Port scan (`port_scan`)

One source touching many distinct destination ports in a short window.

Suggested response:
- Block the scanning IP.
- Review which scanned services must be exposed at all.

### Web scanning / forced browsing (`web_scan`)

Burst of 401/403/404 responses to one client IP.

Suggested response:
- Rate-limit or block the scanning IP.
- Confirm no discovered path exposes sensitive content.

### Account used from multiple IPs (`multi_ip_login`)

Same account authenticated from several IPs (at least one external) in a short window. No GeoIP is used, so this is a heuristic.

Suggested response:
- Confirm with the user whether both locations are legitimate.
- Revoke sessions and require re-authentication if not.

### Off-hours login (`off_hours_login`)

Successful login outside configured business hours.

Suggested response:
- Verify the login with the account owner or on-call roster.

### Successful login after failures (`success_after_failures`)

A login succeeded shortly after failed attempts from the same IP or against the same account.

Suggested response:
- Treat the account as potentially compromised: disable it and revoke active sessions/tokens.
- Reset credentials and re-enrol MFA after the account is verified with its owner.
- Review everything the account did after the successful login.

### Web attack payload in request (`web_attack_payload`)

Request contains SQL injection, XSS, path traversal, command injection or JNDI patterns.

Suggested response:
- Block the source at the WAF and review responses (HTTP 200 on a payload warrants deeper review).
- Patch or harden the targeted application and review its database/app logs.

### Repeated failed logins (brute force) (`brute_force`)

Many failed logins from one source IP inside a short window.

Suggested response:
- Block or rate-limit the source IP at the firewall / WAF.
- Enforce account lockout and MFA on the targeted service.

### MFA prompt flooding (MFA fatigue) (`mfa_fatigue`)

Many denied, rejected or timed-out MFA prompts for one account in a short window. Severity rises when an approved login follows.

Suggested response:
- Contact the user out-of-band and confirm whether they were trying to sign in.
- Reset the password and revoke sessions if any prompt was approved after the flood.
- Switch to number-matching or phishing-resistant MFA and limit the number of push attempts.

### Password spraying (`password_spray`)

One source IP failing against many different usernames.

Suggested response:
- Block the source IP and review all accounts it targeted.
- Force password reset for any targeted account that later logged in successfully.
- Enable MFA and smart-lockout on the authentication endpoint.

### Office application starts a shell (`office_spawns_shell`)

A Word, Excel, PowerPoint, Outlook or OneNote process created PowerShell, cmd, a script host or a LOLBin. This is a common macro-malware pattern.

Suggested response:
- Isolate the host and retrieve the document that was opened (email attachment or download).
- Block Office child-process creation with an attack-surface-reduction rule and disable macros from the internet.
- Search mail and proxy logs for other recipients of the same document.

### Imported Sigma rule match (`sigma_match`)

An event matched a Sigma detection rule that you imported. The finding carries the rule's own title, level and ATT&CK tags.

Suggested response:
- Follow the response guidance in the Sigma rule itself and validate the matched events.

### Suspicious command line (`suspicious_command`)

Command line matches known living-off-the-land or credential-theft patterns.

Suggested response:
- Isolate the host from the network (EDR containment) pending triage.
- Collect the process tree, memory and the decoded payload for analysis.
- Hunt for the same command pattern on other hosts.

### New service, scheduled task or autorun (`persistence_mechanism`)

A service was installed, a scheduled task was created, or a command added an autorun registry key.

Suggested response:
- Check the service, task or registry value against change records and the publisher of the binary it launches.
- Remove the persistence item and collect the referenced binary or script for analysis.
- Hunt for the same service, task name or path on other hosts.

### Sensitive account / audit activity (`sensitive_activity`)

Account creation, privileged group changes or audit-log clearing.

Suggested response:
- Disable any account or group membership that was not change-approved.
- Preserve the affected host's logs/disk image before cleanup (evidence).
- Restore audit logging and forward logs off-host so they cannot be wiped locally.

### Lateral movement (remote services) (`lateral_movement`)

One account or source address logging in to many different hosts in a short window, or remote-execution tooling (PsExec, WMI, WinRM, admin shares) in a command line.

Suggested response:
- Identify the source host and account, and confirm whether an administrator or tool was expected to touch these hosts.
- Disable the account or isolate the source host if the activity is not approved, then review each destination host.
- Restrict remote administration (RDP, SMB, WinRM) to jump hosts and enforce tiered administration.

### Periodic outbound connections (beaconing) (`beaconing`)

One host contacting the same external address and port at a steady rhythm, which is how many implants check in with their controller.

Suggested response:
- Identify the process behind the connections on the source host and check the destination reputation.
- Block the destination at the firewall or proxy and isolate the host if the process is unknown.
- Search other hosts for connections to the same destination.

### Large outbound transfer (`large_outbound`)

Outbound data volume to an external IP exceeds the threshold inside the window.

Suggested response:
- Block the destination IP/domain and capture network evidence.
- Identify what data was on the source host and assess breach-notification duties.

### Event matches recorded IOC (`ioc_match`)

Imported evidence contains an indicator you recorded in the IOC list.

Suggested response:
- Scope the activity: search all other log sources for the same indicator.

## Design notes

- **Burst-based windows.** Events are grouped into bursts separated by less than the window of silence, then tested against the threshold. This keeps evidence lists exact.
- **Spray vs brute force.** A burst touching at least `password_spray.distinct_users` accounts is reported as spraying only, never double-counted as brute force.
- **External means not RFC 1918 / loopback / link-local (IPv6: loopback and fc00::/7).** RFC 5737 documentation ranges used in the sample data therefore count as external.
- **Beaconing** looks at one source host and one external destination and port. It takes the median gap between connections and fires when at least 80% of the gaps are within the configured jitter of that median. It is a rhythm test, not a reputation check, so legitimate update checks and telemetry can match (see the false-positive column).
- **Lateral movement** uses a sliding window over successful logins and counts the distinct destination hosts per source address (or account when there is no address). Remote-execution tooling is matched in command lines separately.
- **Office spawns shell and process rules** need parent and child process information. Windows 4688 and Sysmon event 1 provide it; a CSV without a parent-process column cannot trigger `office_spawns_shell`.
- **Heuristics, not verdicts.** No GeoIP or reputation feeds are used. Every finding lists its evidence event IDs so it can be confirmed or rejected.
- **Imported Sigma rules** run through the same pipeline as built-in rules, so their findings are correlated, redacted, exported and audited the same way. Unsupported constructs are rejected with a reason rather than ignored.

## Adding a rule

1. Write a function `(events, cfg, iocs) -> list[dict]` in `traceforge/detect.py` that returns `_finding(...)` dicts and register it in `RULE_FUNCS`.
2. Add its metadata (including `false_positives` and `remediation`) to `RULES` and its defaults to `DEFAULT_CONFIG` in `traceforge/config.py`; add editable parameters to `PARAMS` if any.
3. Add a minimal data set that makes it fire to `tests/rule_cases.py`, plus a near-miss test in `tests/test_rules.py`. `test_every_rule_has_a_case_and_complete_metadata` fails until you do.
4. Run `python scripts/generate_rule_docs.py` and commit the regenerated file.
